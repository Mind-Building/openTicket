# Changelog

## [Unveröffentlicht]

### Sicherheit

- **Gutschein-Endpoint: Rate-Limit verschärft.** Der öffentliche API-Endpoint `api/voucher_add.php` erlaubt jetzt nur noch **10 statt 30 Requests pro 60 Sekunden je IP** (`ApiGuard::publicApi('voucher', 10, 60)`). Hintergrund: In einer Kundeninstallation legte ein automatisiertes Script (Rechenzentrums-IP, generischer User-Agent) in rund einer Minute ~22 Gutscheine im Warenkorb an und blieb damit knapp unter dem alten 30er-Limit. Das Rate-Limit ist IP-basiert (nicht Session-basiert), neue Sessions umgehen es also nicht; bei Überschreitung antwortet der Endpoint mit HTTP 429, wiederholtes Überschreiten führt zur 1-Stunden-Sperre. (`public/api/voucher_add.php`)
- **CSRF-Schutz flächendeckend im Admin- und Vorverkaufs-Bereich:** Alle 16 bisher ungeschützten Admin-Seiten mit POST-Verarbeitung (u.a. `users_create/edit`, `settings`, `sell`, `customers_edit/import`, `vouchers_create/edit`, `events_create/dates`, `box_office`, `vip_tickets`, `payment_requests`, `payment_request_assign`, `seatplan_categories`) sowie alle 5 Vorverkaufs-Seiten mit POST-Verarbeitung (`sell`, `box_office`, `customers_edit`, `vouchers`, `vouchers_create`) validieren jetzt ein CSRF-Token (`Csrf::validatePost()`); jedes POST-Formular enthält das Token-Feld. Der JSON-Endpoint `seatplan_save.php` validiert das Token per `X-CSRF-Token`-Header, der vom Sitzplan-Editor (`seatplan.php`) mitgeschickt wird. Bei ungültigem Token antwortet die Seite mit HTTP 403.
- **Diagnose-Skript entfernt:** `public/diag.php` (ungeschützt aufrufbar, gab PHP-Version, Serverpfade, DB-Verbindungsdaten und Tabellenliste aus) wurde aus dem Repository gelöscht. **Auf bestehenden Kundeninstallationen muss die Datei manuell gelöscht werden**, da `deploy_to_customer.bat` entfernte Dateien nicht automatisch löscht.
- **Session-Cookie abgesichert:** Das Session-Cookie wird jetzt explizit mit `HttpOnly`, `SameSite=Lax` und (bei HTTPS) `Secure` gesetzt, statt sich auf die php.ini-Defaults zu verlassen. (`app/core/Session.php`, `public/checkout_success.php`)
- **Device-Tokens gehasht gespeichert:** Presales-Gerät-Tokens werden in der Datenbank nur noch als SHA-256-Hash (`sha256:<hex>`) abgelegt — ein DB-Leak gibt damit keine verwendbaren Tokens mehr preis. Bestehende Klartext-Tokens funktionieren unverändert weiter (Cookie und gespeicherte Aktivierungs-URLs) und werden bei der ersten Verwendung automatisch auf das Hash-Format umgestellt. Die Aktivierungs-URL neuer Tokens ist nur noch einmalig bei der Erstellung sichtbar; bei Alt-Tokens bleibt der Kopier-Button bis zum Upgrade erhalten. Migration erforderlich: `database/migrate_device_token_hash.sql` (Spalte `token` auf `VARCHAR(100)`). (`app/models/DeviceToken.php`, `public/admin/users_edit.php`, `database/schema.sql`)
